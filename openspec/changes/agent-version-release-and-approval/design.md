## Context

`AiAgent` 当前把模型、工具、数据集和发布配置集中在 JSON 中，更新接口直接修改记录；广场 `SquarePublishStatus` 只描述内容审核。详见 proposal.md。

## Goals / Non-Goals

**Goals:**

- 以版本快照作为运行时唯一配置来源。
- 建立环境晋级、审批、灰度、指标门禁和回滚数据模型。
- 为旧 Agent 生成兼容 v1 快照并保持 API 迁移可逆。

**Non-Goals:**

- 不在本 change 内选择具体评测供应商或实现全部红队用例。
- 不允许通过版本流程绕过租户授权和凭据/工具策略。

## Decisions

1. **版本快照存 JSON + 哈希。** 保留可读快照便于审计和差异比较，使用规范化 JSON 生成 SHA-256 配置哈希防篡改；生产引用版本 ID 与哈希。
2. **发布状态独立于内容审核。** 一个 Agent 可被广场审核通过但未发布到企业生产，避免市场内容流程成为安全审批捷径。
3. **发布记录与版本分离。** `agent_releases` 记录环境、分群、状态、审批和指标，版本本身不可变；同一版本可安全灰度多个环境。
4. **运行时版本解析集中化。** Agent Chat、自动化和渠道入口统一调用 VersionResolver，禁止各入口自行读取旧 JSON。
5. **回滚使用流量指针。** 回滚只切换环境/分群到既有批准版本，避免复制或编辑配置，减少恢复时间。

替代方案：直接给 `AiAgent` 增加 `version` 字段无法保留历史和并行灰度；Git 管理配置无法绑定数据库资源和运行时审计，因此不采用。

## Risks / Trade-offs

- [Risk] 版本快照引用的模型/数据集/工具被删除 → Mitigation：发布时锁定依赖版本或创建不可删除引用，删除前检查活动发布。
- [Risk] 旧 API 继续改写生产配置 → Mitigation：运行时只读版本，旧更新接口转为新草稿并返回迁移提示。
- [Risk] 灰度指标样本不足导致误判 → Mitigation：配置最小样本、观察窗口和人工确认，不自动扩大高风险流量。
- [Risk] 快照包含敏感提示词或凭据 → Mitigation：快照只存凭据引用，敏感字段按分类脱敏并限制查看。

## Migration Plan

1. 新增版本、发布、审批和依赖锁定表；为现有 Agent 生成 v1 draft/approved 快照。
2. 上线 VersionResolver 双读，比较旧 JSON 与快照的运行结果和配置哈希。
3. 允许内部租户通过新发布流程；旧发布接口仅创建 draft，不直接改变生产指针。
4. 开启生产只读版本和回滚指针，保留旧字段一个发布周期后再清理。
5. 若出现运行差异，按 Agent 关闭新解析 feature flag，保留快照和审计以便修复。

## Open Questions

- 生产审批是否强制双人以及哪些风险等级需要安全委员会参与，可由租户策略配置，不改变基础状态机。

## Browser Acceptance Design

- 目标控制台入口：`/agents/:id/release`（或控制台 Agent 版本/发布页的等价入口）。
- 种子数据：一个拥有 DEV/TEST/PROD 指针的 Agent、两份有差异的版本、一个通过门禁版本、一个失败门禁版本、测试 cohort 和回滚目标。
- 正向流程：打开版本列表 → 查看 diff/依赖 → 提交评审 → 以审批账号批准 → 灰度 cohort → 查看 active version → 执行回滚 → 刷新。
- 负向流程：无审批权限用户、失败门禁版本、过期 revision 重复点击发布/回滚，均应在 UI 呈现原因且不改变指针。
- 证据：截图/录屏、版本 hash、cohort、审核人、回滚前后 active version 和审计事件 ID。
- 浏览器自动化必须使用可重置的测试 Agent 和 sandbox 工具；发布失败、审批过期和回滚测试不得影响真实生产指针。
