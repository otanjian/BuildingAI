## Context

现有认证守卫主要建立 `User` 身份，资源实体普遍没有 `tenantId`/`projectId`，部分服务按 `createBy` 或资源 ID 查询。详见 proposal.md；本设计只建立所有后续企业化能力依赖的授权上下文。

## Goals / Non-Goals

**Goals:**

- 建立租户、组织、项目、成员和资源授权的持久化模型。
- 让控制器守卫和服务层查询共享同一个已验证的请求上下文。
- 支持兼容迁移、权限缓存失效和跨租户安全测试。

**Non-Goals:**

- 不替换现有登录协议；不在本 change 内接入企业 IdP。
- 不改变具体资源的业务字段或 Agent 发布流程。

## Decisions

1. **租户作用域采用显式列而非仅靠 PostgreSQL session variable。** 核心表直接存 `tenantId`/`projectId`，便于 TypeORM 查询、索引、导出和逐步迁移；模型目录等平台资源保留显式 `scope=PLATFORM`，数据库 RLS 可作为后续纵深防御。
2. **成员关系独立于现有单角色 User。** `tenant_memberships` 支持一个用户加入多个租户和部门，旧 `User.role` 在迁移期映射为默认角色；业务权限以成员关系为准。
3. **RBAC 与 ABAC 组合。** RBAC 提供可理解的角色，ABAC 处理项目、分类、环境、时间和工具风险条件；策略决策结果带版本，供审计和缓存失效使用。
4. **服务层二次授权。** 控制器守卫用于早期拒绝和统一错误，Repository/Service 查询必须强制附加租户条件，避免内部调用或异步任务绕过 HTTP 守卫。
5. **双阶段迁移。** 先加可空列和新表并回填，再启用新写入门禁和非空约束；这样可在发现映射错误时切回旧读路径。

6. **公开请求使用服务端解析。** 匿名 Agent/API key 请求从已验证的发布凭据和 Agent 版本解析租户，不创建可伪造的匿名租户上下文；渠道和 Worker 也必须从受信任的服务身份/任务记录解析。

替代方案：仅按用户拥有者隔离无法满足协作；仅新增单一 `tenantId` 而无成员/资源授权无法支持部门和项目；一次性切换会放大迁移风险，因此不采用。

## Risks / Trade-offs

- [Risk] 旧数据无法唯一映射到租户 → Mitigation：进入待认领队列，默认不可见，不做猜测性开放。
- [Risk] 权限缓存导致成员已停用仍可访问 → Mitigation：使用 `tenantId:userId:policyVersion` 键，高风险操作绕过过期缓存并在变更时主动失效。
- [Risk] 漏改某个资源查询造成越权 → Mitigation：建立资源访问清单、服务层统一 Scope helper、跨租户集成测试和静态检索检查。
- [Risk] 查询增加 tenant/project 条件后性能下降 → Mitigation：核心表补组合索引并使用压测基线。

## Migration Plan

1. 盘点 User、Agent、Dataset、Conversation、Automation、MCP、Credential、Usage 等表和拥有者映射。
2. 创建租户/组织/成员/项目/授权表，核心资源新增可空 `tenantId`/`projectId` 和索引。
3. 回填可确定资源，无法确定的资源进入受限队列；双写新创建资源。
4. 对内部试点租户启用服务层租户 Scope，比较旧新读结果并运行越权测试。
5. 启用“新写入租户必填”，逐步将核心列收紧为非空；保留旧 API 一个发布周期。
6. 失败时通过 feature flag 切回旧读路径，保留新列和审计数据，不执行破坏性回滚。

## Open Questions

- 是否在第一阶段为所有租户启用 PostgreSQL RLS，还是先采用应用层 Scope + 数据库最小权限？这不改变本 change 的外部契约，可在容量和运维评估后决定。

## Browser Acceptance Design

- 目标控制台入口：`/console/tenant`（若菜单采用其他路径，必须提供等价的可发现入口）。
- 浏览器种子数据：租户 A/B、A 的管理员/项目成员、B 的私有 Agent 和数据集、一个待邀请用户。
- 正向流程：登录 → 选择租户 A → 打开成员管理 → 邀请用户 → 分配项目角色 → 刷新 → 观察成员和有效权限持久化。
- 负向流程：在租户 A 浏览器会话中打开租户 B 资源链接，验证安全的 403/404、无资源标题/所属租户泄露、无状态变更。
- 证据：保存浏览器截图或录屏、请求失败状态、刷新后的页面和对应审计事件 ID；不得把真实邮箱、token 或企业数据放入测试证据。
- 浏览器自动化必须使用隔离测试账号和可重复种子/清理脚本；仅调用 API 或查看数据库不能标记本任务完成。
