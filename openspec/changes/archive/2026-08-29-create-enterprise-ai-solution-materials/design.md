## Context

本变更只新增售前与交付文档，不改动运行时代码。现有项目能力来源于各自 README 与已完成 OpenSpec 变更：BuildingAI 提供企业级 Agent、MCP、RAG、知识库、模型聚合和计费基础；Doris 提供只读分析查询与 SAP 业务语义 MCP；AIP 提供 AI 应用、知识库、流程编排和嵌入式集成；OpenCode 提供 AI Coding Agent。方案需把这些能力组织成客户可理解的产品组合。

## Goals / Non-Goals

**Goals:**

- 产出一份独立、可打印、面向客户的中文 Markdown 方案。
- 用统一参考架构连接数据、模型、Agent、业务系统和研发工具。
- 给出可落地的 PoC、规模化和运营治理方法。

**Non-Goals:**

- 不替代客户的详细需求规格、网络安全方案或报价书。
- 不锁定单一云厂商、模型供应商或硬件规格。
- 不把演示数据或模拟指标当作客户承诺。

## Decisions

1. **采用三层价值模型作为主线。** 经营层回答“发生了什么、为什么、怎么办”；操作层执行受控的跨系统动作；开发层把需求转化为可测试的软件交付。备选是按产品目录组织，但不利于客户从业务目标理解方案。
2. **采用能力矩阵而非产品宣传。** 每个项目写明输入、输出、接口和责任边界，减少“一个平台包打天下”的误解。
3. **采用数据平面、智能平面、执行平面、治理平面四平面架构。** 该结构能同时容纳 Doris/SAP 数据、模型与 RAG、MCP/工作流/业务 API，以及横向安全审计。
4. **采用“先只读、后建议、再审批执行”的风险分级。** 高风险动作默认人工确认，便于在 PoC 中快速验证价值并控制生产风险。
5. **文档与实现解耦。** 交付文档发布在 `docs/`，OpenSpec artifacts 记录范围、规格和任务；客户项目按调研结果替换示例系统与指标。

## Risks / Trade-offs

- [数据口径不一致] → 建立指标字典、业务语义元数据和口径审批人；先锁定 10–20 个核心指标。
- [模型幻觉或越权执行] → RAG 引用、工具白名单、参数校验、审批流、全量审计和回滚。
- [集成周期过长] → 先选一个闭环场景，使用标准 REST/MCP/SQL 接口，保留人工导入兜底。
- [收益难量化] → PoC 前采集基线，按准确率、时效、自动化率和人工节省核算。
- [供应商与模型波动] → 通过模型路由、私有化可选架构和数据可迁移设计降低锁定。

## Migration Plan

1. 复制方案模板，完成客户调研和数据/系统清单。
2. 选择一个低风险场景建设 PoC，默认只读和人工审批。
3. 通过验收后扩展到更多部门、数据域和执行动作。
4. 上线前完成安全评审、运维交接和回滚演练；若未达标，保留原系统流程并下线 Agent 入口。
