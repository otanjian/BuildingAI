## Context

现有实现已经有 `tenants` 和 `tenant_memberships` 表，但用户列表仍直接查询全局 `User`，权限守卫主要读取全局角色，租户页面还暴露组织、项目和资源授权概念。现有兼容迁移只在检测到 root 用户时创建默认租户，并不能保证指定的“谭建”成为管理员，也没有覆盖所有业务实体。

## Goals / Non-Goals

**Goals:**

- 以 `TenantMembership` 作为用户访问租户的唯一关系来源。
- 使用服务端验证的当前租户上下文保护所有租户业务读写。
- 支持一个用户加入多个租户、设置默认租户并切换当前租户。
- 让默认租户回填覆盖现有租户业务内容，并把谭建标记为平台管理员和默认租户管理员。
- 让账号管理与租户成员管理在 API 和 UI 上职责清晰。

**Non-Goals:**

- 本变更不删除已有组织、项目、资源授权表，也不实现项目内权限。
- 本变更不接入新的 OIDC、SAML、SCIM 或 MFA 协议。
- 本变更不改变平台公共模型目录、系统菜单和平台角色的共享属性。

## Decisions

1. **保留 User 与 TenantMembership 分离。** `User` 表示全局身份；`TenantMembership` 表示用户是否能访问某租户。这样支持多租户用户，且不把一个 `tenantId` 错误地放到 User 作为权限依据。
2. **使用 tenants.admin_user_id 表示唯一当前管理员。** 管理员必须是该租户的 active 成员；直接修改该字段即可完成管理员更换，不增加审批或转移工作流。旧 owner/admin 角色在兼容期映射为管理员。
3. **请求租户由已验证上下文确定。** 保留 `x-tenant-id` 作为客户端选择提示，但每次请求都通过成员关系和租户状态验证；请求体中的 tenantId 不具有授权效果。前端缓存键必须包含 tenantId。
4. **默认租户迁移采用确定性匹配和幂等回填。** 按 username、email、nickname 或 realName 精确匹配“谭建”；若无法唯一匹配则回退到最早的 root 用户并记录警告。默认租户按 code=`default` 唯一创建。当前存量租户业务记录（包括已有演示租户归属）统一迁入默认 tenantId，用户通过成员关系加入默认租户；后续新记录由 API 按当前上下文隔离。
5. **租户业务范围通过统一 Scope helper 强制。** 列表、详情、搜索、执行、异步任务和写入路径统一从请求上下文注入 tenantId；跨租户资源返回安全的 not-found。平台级表不增加伪造的租户归属。
6. **先兼容后收紧。** 迁移先补列并回填，应用确认新写入总有 tenantId 后再逐步将核心业务列改为 NOT NULL；无法确定归属的旧记录不开放给普通租户。

## Risks / Trade-offs

- [Risk] “谭建”存在多个相似账号 → Mitigation：只接受唯一精确匹配；否则选择最早 root 并写入迁移日志，部署后由平台管理员复核。
- [Risk] 旧表遗漏 tenantId 导致越权 → Mitigation：建立实体清单、统一 Scope helper、静态检索和跨租户集成测试。
- [Risk] 全局禁用用户与单租户暂停状态混淆 → Mitigation：保留 User.status 与 TenantMembership.status 两级状态，分别表示登录和租户访问。
- [Risk] 切换租户后显示旧数据 → Mitigation：所有查询 key 包含 tenantId，切换时清理租户业务缓存。

## Migration Plan

1. 发布默认租户与成员关系回填迁移，保证重复执行不会重复创建并保持当前存量业务记录归属默认租户。
2. 将“谭建”设置为平台管理员，并写入默认租户 `admin_user_id`；为现有用户建立默认租户 active membership。
3. 将现有租户业务表中的空 tenantId 归入默认租户，保留迁移统计和警告。
4. API 切换到成员关系验证和租户 Scope，用户列表改为当前租户成员列表。
5. Web 增加租户选择和成员管理，隐藏尚未实现的复杂项目/授权演示入口。
6. 完成类型检查、单元测试、迁移 rehearsal 和跨租户负向验证后，再收紧新写入租户字段。
