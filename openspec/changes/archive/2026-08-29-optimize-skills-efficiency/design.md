## Context

See proposal.md for motivation. The source of truth is `skills/`; editor copies are generated by `scripts/sync-skills.mjs`. The repository currently contains three overlapping meta-skills, a 297-line PostgreSQL body, stale architecture notes, and scripts that delete and recopy target directories.

## Goals / Non-Goals

**Goals:**

- Keep commonly needed instructions in concise `SKILL.md` files and defer specialist material to directly linked references.
- Ensure descriptions and paths reflect the current repository and installed AI SDK version.
- Preserve existing skill names and user-visible quality while preventing accidental multi-skill overlap.
- Avoid unnecessary package installation, network access, directory deletion, and file copying during normal skill workflows.
- Provide deterministic lint and sync behavior that can be verified without touching application code.

**Non-Goals:**

- Building a new skill activation hook system.
- Measuring model quality statistically in this change.
- Automatically deleting existing user/editor configuration.

## Decisions

### Keep compatibility names, consolidate bodies

Retain `skill-creator`, `skill-writer`, and `skill-developer` directories for compatibility, but make `skill-creator` the authoring entry point, turn `skill-writer` into a short redirect, and keep `skill-developer` focused on trigger/hook runtime behavior. This avoids broken references while preventing three full bodies from activating for one request.

### Progressive disclosure by task frequency

Keep a short default workflow in `postgresql-table-design` and move data-type, indexing, JSONB, partitioning, and extension details into references. Keep project architecture as a navigation map and require live path verification before relying on a stale-looking detail.

### Local-first AI SDK lookup

Use the installed `node_modules/ai` and provider package as the first source. Network lookup is a fallback only when local docs are unavailable or the user explicitly asks for current external documentation. Never recommend an upgrade merely because the question is uncertain.

### Incremental synchronization

Add a `--dry-run` mode and compare source/target files by size and modification time plus content when needed. Unchanged files are skipped; changed files are copied without deleting the whole skill directory. Existing command forms remain valid.

### Lint as a fast, read-only check

Add `pnpm skills lint` backed by a small Node script. It checks frontmatter through the existing validator, body line budgets, local Markdown links, and known stale project terms. It reports actionable failures and exits non-zero without modifying files.

## Risks / Trade-offs

- [Risk] Moving details to references could make a specialized task miss context. → Keep explicit links and task-to-reference routing in each lean skill.
- [Risk] Incremental sync could leave deleted source files in a target. → Remove target files that are absent from the source only within the selected skill directory, and test this behavior.
- [Risk] Narrower descriptions could reduce activation recall. → Preserve concrete trigger phrases and add positive/negative lint fixtures; do not remove existing skill names.
- [Risk] Repository facts can drift again. → Add lint checks for the currently known stale terms and require live verification language in architecture guidance.

## Migration Plan

1. Rewrite skill bodies and add references without changing directory names.
2. Add lint and sync tests, then run lint and a dry-run against the current workspace.
3. Run a real single-skill sync for the configured editor only if verification shows no unintended deletes.
4. Rollback is a normal revert of the skill and script changes; generated editor copies can be regenerated.
